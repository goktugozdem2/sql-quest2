AI SQL validation

How to Validate AI-Generated SQL: 7 Checks Before Production

AI can produce syntactically valid SQL in seconds. The dangerous query is the one that runs, returns plausible numbers, and quietly answers the wrong question.

Published September 9, 20269 min readBy Can Goktug Ozdem, Founder of SQL Quest

Short answer: define the expected result first, check the referenced schema, test filters and NULLs, measure join cardinality, confirm aggregation grain, compare against known rows, and inspect both the result and query plan. Never approve a production query from syntax alone.

Seven checks

  1. Write the result contract
  2. Verify the schema
  3. Challenge filters and NULLs
  4. Measure join cardinality
  5. Confirm grain and denominator
  6. Compare with known rows
  7. Inspect safety, cost, and the plan

A worked example: “paid customers in the last 30 days”

Suppose an AI assistant returns this query:

Plausible, executable, and still ambiguous
SELECT c.customer_id, c.email, p.paid_at
FROM customers AS c
JOIN payments AS p
  ON p.customer_id = c.customer_id
WHERE p.status != 'refunded'
  AND p.paid_at >= '2026-08-10';

It looks reasonable. It may still be wrong:

  • One customer can have several payments, so the output may duplicate customers.
  • status != 'refunded' includes statuses such as pending or failed.
  • Rows with a NULL status do not pass the filter because a SQL WHERE clause keeps only expressions that evaluate to true.
  • “Paid customer” might mean a recent successful payment, an active subscription, or a lifetime buyer. Those are different contracts.

If the agreed definition is “one row per customer with at least one successful payment on or after August 10, 2026,” make that grain explicit:

One testable definition, expressed in SQL
WITH recent_paid_customers AS (
  SELECT
    customer_id,
    MAX(paid_at) AS latest_paid_at
  FROM payments
  WHERE status = 'paid'
    AND paid_at >= '2026-08-10'
  GROUP BY customer_id
)
SELECT
  c.customer_id,
  c.email,
  r.latest_paid_at
FROM recent_paid_customers AS r
JOIN customers AS c
  ON c.customer_id = r.customer_id
ORDER BY r.latest_paid_at DESC;

This version is not better because it is longer. It is better because the intended grain and accepted payment state are explicit and testable.

Check 1: write the result contract before reviewing the query

State four things in plain language:

  1. What does one output row represent?
  2. Which records must be included and excluded?
  3. Which time zone and date boundaries apply?
  4. What should happen when a value is missing?

For the example, the contract is “one row per customer, with at least one paid payment in the fixed period, ordered by the latest qualifying payment.” That sentence is a stronger review tool than “the query looks right.”

Check 2: verify every table, column, and relationship

Confirm that the query uses the real schema, not names invented from a prompt. Check primary keys, foreign keys, column types, and whether timestamps represent creation, settlement, or update time. If the assistant did not receive the schema, treat its output as a draft rather than an executable answer.

Check 3: challenge filters, NULLs, and boundaries

Test each predicate separately. In SQLite, rows are removed when a WHERE expression evaluates to false or NULL. Nullable columns therefore create silent omissions. Check:

  • equality versus an explicit list of accepted statuses;
  • IS NULL and IS NOT NULL behavior;
  • inclusive versus exclusive date boundaries and time zones;
  • empty strings, zero values, and sentinel values.

A test dataset containing only clean rows proves almost nothing. Create at least one fixture for every edge case. If NULL behavior is the weak point, use the SQL NULL review guide before approving the query.

Check 4: measure join cardinality before and after the join

Ask what relationship each join represents: one-to-one, one-to-many, or many-to-many. Then measure it.

Compare row grain with entity grain
SELECT
  COUNT(*) AS joined_rows,
  COUNT(DISTINCT c.customer_id) AS distinct_customers
FROM customers AS c
JOIN payments AS p
  ON p.customer_id = c.customer_id
WHERE p.status = 'paid'
  AND p.paid_at >= '2026-08-10';

If joined_rows is much larger than distinct_customers, the query may be correct at payment grain but wrong at customer grain. Adding DISTINCT can hide the symptom without proving the relationship is correct. The SQL joins guide works through the underlying one-to-many shapes.

Check 5: confirm aggregation grain and denominator

Every metric needs an explicit numerator, denominator, and grouping level. For conversion rate, decide whether the denominator is visitors, sessions, eligible accounts, or leads. For revenue, decide whether refunds, tax, credits, and currency conversion are included.

Review every selected column in an aggregate query. SQLite permits some bare columns that are neither aggregated nor included in GROUP BY, but their selected value can be arbitrary. A query that runs may therefore still communicate an unstable or non-portable result. Review the GROUP BY failure modes if the metric collapses several rows into one.

Check 6: compare with known rows and an independent calculation

Choose a small period you can verify manually. Keep examples that should definitely be included and definitely be excluded. Compare:

  • total rows and distinct entities;
  • a hand-calculated subtotal;
  • minimum and maximum dates;
  • a few known IDs;
  • the previous trusted report, if its definition matches.

Try to falsify the query. A useful test is designed to make the SQL fail if its assumptions are wrong. Repeating the happy path only shows that the example was easy.

Check 7: inspect safety, cost, and the query plan

Use a read-only account for review. Add a sensible row limit during exploration. Keep write operations behind separate permissions and explicit human approval. For performance, use EXPLAIN QUERY PLAN as a diagnostic aid, but do not build application logic that parses its display format: SQLite documents that the format can change between releases.

Syntax, semantics, performance, and operational safety are four separate checks. Passing one does not imply the others.

AI SQL validation checklist

  • One output row is clearly defined.
  • Tables and columns exist and have the expected types.
  • Status and date rules match the business definition.
  • NULL cases have explicit expected behavior.
  • Join cardinality is measured, not guessed.
  • Aggregation grain and denominator are stated.
  • Known positive and negative examples pass.
  • The query runs with read-only access and a safe limit.
  • The result, not only the SQL text, has been reviewed.
  • Performance is acceptable on representative data.

Frequently asked questions

Can AI-generated SQL be trusted if it runs without an error?

No. Execution proves that the engine accepted the statement. It does not prove that the query matches the business definition, returns the right grain, handles missing data, or avoids duplicates.

Should I use DISTINCT to remove duplicates from an AI query?

Only after you understand why duplicates exist. DISTINCT may be correct for the intended result, but it can also hide a bad join or an undefined entity grain.

What is the fastest way to test an AI-generated SQL query?

Write the expected row grain, run it on a tiny dataset with known edge cases, compare distinct counts before and after joins, and manually verify several included and excluded rows.

Is EXPLAIN QUERY PLAN enough to validate SQL?

No. It helps investigate how SQLite plans a query. It does not validate the meaning of the result.
