Read the tasks again and one thing stands out: almost every one is a question about people on a table of events. Monthly active users, the top 10% of users, a cohort, a funnel, a conversion rate. The table has one row per transaction; the answer has one row per user, or one number over users. The traps below all live in that gap between the grain of the table and the grain of the question.

Two of the named tasks, monthly active users with completed transactions and the top 10% of users by volume, are the written questions of our 60-minute Revolut-style mock, so this page does not solve them. The three traps below are different questions on the same data.

Trap 1: a transfer is two rows

Question: how much money did users send each other, in GBP? A peer-to-peer payment between two users of the same app is written twice: a transfer_out on the sender and a matching transfer_in on the receiver. Sum both legs and you count every pound twice. Forget the status filter and you also count transfers that were declined or reversed.

wrong: both legs, every status
SELECT ROUND(SUM(amount_gbp), 2) AS p2p_volume_gbp
FROM transactions
WHERE type IN ('transfer_out', 'transfer_in');

That returns 89,814.86.

right: one leg, completed only
SELECT COUNT(*) AS transfers,
       ROUND(SUM(amount_gbp), 2) AS p2p_volume_gbp
FROM transactions
WHERE type = 'transfer_out'
  AND status = 'completed';
transfersp2p_volume_gbp
34544469.97

The wrong answer is about double the right one, which is exactly the kind of number that looks plausible on a screen with a clock running. Before you sum, say out loud what one row is. Here one transfer is two rows, and a status other than completed is money that never moved.

Trap 2: an average that skips the people with no spend

Question: average card spend per user in August 2026, by plan. The natural first query aggregates spend per user and joins it to users. Users who made no completed card payment that month come out of the LEFT JOIN with a NULL, and AVG ignores NULLs. So the "average per user" is really the average per spending user.

the NULL decides the ranking
SELECT u.plan,
       COUNT(*) AS users,
       ROUND(AVG(s.spend_gbp), 2) AS avg_spenders_only,
       ROUND(AVG(COALESCE(s.spend_gbp, 0)), 2) AS avg_spend_gbp
FROM users u
LEFT JOIN (
  SELECT user_id, SUM(amount_gbp) AS spend_gbp
  FROM transactions
  WHERE type = 'card_payment'
    AND status = 'completed'
    AND ts >= '2026-08-01' AND ts < '2026-09-01'
  GROUP BY user_id
) s ON s.user_id = u.user_id
GROUP BY u.plan
ORDER BY avg_spend_gbp DESC;

Without COALESCE, plus looks like the top plan. With it, premium is. Neither number is wrong in itself; they answer different questions. Ask which one is wanted, then write that one on purpose. Note the date filter too: ts < '2026-09-01' keeps every timestamp on 31 August, which a BETWEEN '2026-08-01' AND '2026-08-31' would drop (see the BETWEEN trap).

Trap 3: a funnel with a moving denominator

Question: of everyone who signed up, how many verified, topped up, and then paid by card? A funnel is only a funnel if each step is a subset of the one before. Count each step on its own and a user who paid without a recorded top-up inflates a later step, so the rates stop meaning anything. Build one row per user with a flag per step, then require every earlier step.

one row per user, then nested steps
WITH steps AS (
  SELECT u.user_id,
         u.kyc_verified_at IS NOT NULL AS verified,
         EXISTS (SELECT 1 FROM top_ups t WHERE t.user_id = u.user_id) AS topped_up,
         EXISTS (SELECT 1 FROM transactions x
                 WHERE x.user_id = u.user_id
                   AND x.type = 'card_payment'
                   AND x.status = 'completed') AS paid
  FROM users u
)
SELECT COUNT(*) AS signed_up,
       SUM(verified) AS verified,
       SUM(verified AND topped_up) AS topped_up,
       SUM(verified AND topped_up AND paid) AS paid_by_card,
       ROUND(100.0 * SUM(verified AND topped_up AND paid) / COUNT(*), 1) AS signup_to_card_pct
FROM steps;
signed_upverifiedtopped_uppaid_by_cardsignup_to_card_pct

EXISTS keeps the grain at one row per user, so a user with forty card payments counts once. The 100.0 forces decimal division; with 100 SQLite divides integers and rounds the rate down to a whole number.

A 2-week plan

  • Days 1–3: the grain. Per-user and per-month aggregates on a transactions table, with the status filter every time. Start with Revolut question 1, Monthly Spend Per Account.
  • Days 4–6: joins and NULLs. LEFT JOIN plus COALESCE, anti-joins for "users who never did X", WHERE against HAVING. Joins practice · NULL handling.
  • Days 7–9: CTEs and cohorts. Signup cohorts, activation within N days, funnels built as above. CTE practice.
  • Days 10–11: window functions. Deciles with NTILE, month-over-month with LAG, top N per group. Window functions practice.
  • Days 12–14: under the clock. Sit the 60-minute screen as one block: multiple choice read off query output, then two written queries. Review every miss before you sit it again.

FAQ

How long is the Revolut data analyst SQL screen?

Candidate reports collected in interviewquery's 2026 guide (stamped Interviewed Q3 2026) describe a HackerRank screen of about 60 minutes: one report says "60 minutes, with two SQL questions and several" multiple-choice items. An earlier edition of the same guide gave 30 minutes. Revolut does not publish the format, so treat both as candidate-reported.

What does the Revolut live SQL round ask?

The same guide describes "four sequential questions on a set of interconnected tables (users, transactions, events, subscriptions)", naming monthly active users with completed transactions, users in the top 10% by transaction volume, joins, aggregations, CTEs, filtering and date logic. Other candidates add window functions, cohort or funnel questions and conversion rates, and WHERE vs HAVING and NULL handling with COALESCE.

Which SQL topics should I practice for a Revolut data analyst interview?

The topics the reports name: joins, GROUP BY and aggregation, WHERE vs HAVING, NULL handling with COALESCE, CTEs, window functions, date logic, cohorts, funnels and conversion rates. Most of the named tasks ask about users on a table of transactions, so practise getting the grain right: one row per user or per month, with a status filter on every money query.
