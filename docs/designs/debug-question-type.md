## Problem Statement

The founder asked whether SQL Quest could also serve "AI education". In the
session the meaning was narrowed to option B, teaching **people** the SQL skill
the AI era asks for. Option A, licensing the bank to AI companies as training
or eval data, is out for now. The narrowest true version of B is reading a
query someone else (or an AI) wrote and fixing it. That is a skill interviews
already test, and the product does not teach it today: every challenge starts
from a blank editor.

## Demand Evidence

- **No direct demand yet.** The founder's answer (D2) was "Henüz kimse,
  sezgi". In 90 days of GSC data:
  - `/blog/validate-ai-generated-sql/`: 661 impressions, 12 clicks;
  - `/sql-for-the-ai-era/`: 245 impressions, 3 clicks;
  - AI-related queries ("sql ai engineer" and similar): about 30 impressions;
  - none of the 9 payers ever arrived through these pages.
- **Indirect evidence that interviews test the skill.** R1's dossiers found
  "read or debug an existing query" rounds in 3 dated reports at 2 companies:
  - TikTok: a data-scientist report (Jun 2026) and a data-engineer report (Sep 2025);
  - Shopify: the online assessment, with a "find the bug in this query" item.

  This is the case for building the item type: it serves the paying
  population, which is interview-shaped, whether or not "AI" is the hook.

## Status Quo

Candidates practise writing SQL from scratch: here, on DataLemur, StrataScratch
and LeetCode. Reading someone else's wrong query, and spotting the fan-out or
the NULL trap, is practised only by accident, in their own mistakes.

The trap pages (`src/data/sql-patterns.js`) already explain five classic bugs
in prose. None of them is something a person can do.

## Target User & Narrowest Wedge

**Who:** the existing buyer, a data-analyst candidate with an interview on the
calendar. In particular those preparing for companies whose dossiers report
debug rounds (TikTok, Shopify).

**The wedge:** a set of Debug items inside the existing Practice bank, under
the existing free quota and Pro boundary. No new product, brand or price.

## Constraints

- **SEO loop rule 1:** S1 is RED (Bing's index is about 1.9× the sitemap), so
  no new indexable page ships. Discovery goes through existing pages: the trap
  pages, `/sql-for-the-ai-era/`, the validate-AI post and company pages.
- **Decision 2026-11-22: no 10th Skillmap axis.** The founder's pick (B)
  mentioned putting debug on the Skillmap. This design keeps the nine axes.
  Debug items are tagged with the canonical skill of the bug, and debug
  accuracy is shown as its own stat. Revisit an axis when the type has 15 or
  more items and 28 days of data, the same rule as DDL/DML.
- **No claims about interview frequency.** The company tie-in cites the dated
  dossiers only.
- **Quota:** a Debug solve counts toward the 10 free solves like any challenge.
- The usual fragile areas apply: hooks above the early returns, no raw-order
  pick, deep links that start guest mode and return.

## Premises (agreed, D3)

1. "Read and fix an AI-written query" is part of interview prep, not a
   separate market. The buyer is the same person.
2. Demand is unproven, so there is no separate product, brand or price. Ship a
   set and measure it.
3. Data and eval licensing is out of scope until O2 (10 payers per 30 days by
   2027-02-08).

## Approaches Considered

- **A. Minimal: 8–10 "this query is wrong, fix it" items in the existing
  format.** Rejected by the founder in favour of B. It teaches the fix but not
  where the defect is.
- **C. "Check the AI's suggestion":** the tutor deliberately proposes a flawed
  query. Rejected because it erodes trust in the tutor.

## Recommended Approach: B, a Debug question type (founder's choice, D4)

**Item shape** (a `type: 'debug'` entry in `src/data/challenges.js`, ids **331 to 342**; #172 claims 325–329 and #236 claims 330):
- `brokenQuery`: prefilled in the editor. The framing line is "An AI assistant
  wrote this for the task below. It returns the wrong answer."
- `bugLines`: the 1-based line(s) where the defect is.
- `bugKind`: a key of `src/utils/error-patterns.js`. That file is the one
  enum. Add `fan_out` and `date_upper_bound` there, each with its
  description and a fire/no-fire test pair.
- The usual dataset, expected output and reference fix. The Skillmap credit
  comes from the item's existing `skills`/`category` tags, the same as any
  challenge; there is no new mapping.
- Turkish fields: `description_tr`, `hint_tr`, and Turkish comments in
  `brokenQuery`. The framing line is an i18n key (EN and TR).
- SQLite only. The date-boundary item uses `strftime` / ISO strings, never
  `DATE_TRUNC`.

**Flow:**
1. **Spot.** The person taps the line they think is wrong. The challenge
   editor (CodeMirror) runs with `lineNumbers: false` today, so debug items
   turn on line numbers and a `gutterClick` handler. Spot is optional and
   scored separately in `debugStats`, never a gate to the fix.
   - **Prefill:** `brokenQuery` fills the editor only when
     `challengeQueries[id]` holds no saved draft. A "Reset to the AI's query"
     button restores it.
   - **Starter:** debug items skip the first-run starter branch
     (app.jsx ~24093).
2. **Fix.** They edit and Submit, graded by the same engine as any challenge.
   A Run on the unmodified broken query shows its wrong output next to the
   expected output, so the defect is visible.
3. **Learn.** On a solve, one line says what the bug was ("JOIN fan-out:
   orders repeat once per item"), with a link to the matching trap page where
   one exists.

**Diagnosis in v1:** the existing `diagnose.js` / `primaryHint` sentence
only. Per-kind "the bug is still there" detectors come in v2, each with a
fire/no-fire test pair; they are new static analysis.

**Skillmap and stats:**
- A solve credits the item's canonical skills through its existing tags.
- A new `debugStats` record (spots correct ÷ attempted, fixes solved ÷ attempted)
  is shown on the profile and in the Coach. It is not a radar axis.

**Initial set: 12 items.** Six reuse the five trap-page patterns (NOT IN with
NULL, join fan-out, BETWEEN on timestamps, average of averages, LEFT JOIN
WHERE filter) plus a missing GROUP BY column. Six are new:
- the wrong window partition;
- ties in RANK vs ROW_NUMBER;
- integer division;
- COUNT(*) vs COUNT(col);
- DISTINCT hiding duplicates;
- a date truncation boundary.

Mix: 4 Easy, 5 Medium, 3 Hard. Reused trap patterns must not reuse the
Capital One mock's questions or answers (`tests/sql-patterns.test.js`).

Two items carry TikTok/Shopify company tags, citing the dated dossiers
`docs/reads/companies/tiktok.md` and `docs/reads/companies/shopify.md` (on main
since #207/#211). The company-page lists those tags change are test-pinned;
update the pins in the same PR.

**No `/questions/` pages for debug items in v1.** S1 is RED and the loop allows
no new indexable page. `scripts/build-question-pages.mjs` and its sitemap block
skip `type: 'debug'`, with a test. When S1 is green the exclusion is lifted in
its own PR.

**Count guards.** The bank goes from 304 (plus open PRs) to about 316. The
"300+" floor holds, but the exact difficulty and topic splits move. Run
`tests/site-counts.test.js` and the topic and company count tests.

**Discovery (no new pages):**
- a "Debug" filter chip on Practice;
- a line on each trap page: "Fix this bug yourself: question N";
- a section on `/sql-for-the-ai-era/` and the validate-AI post;
- the company pages for TikTok and Shopify name the debug items in their topic
  block.

**Flag:** `debugQuestions`, off until the set and its tests land. The
orchestrator flips it, in its own decision row.

## Open Questions

- Should the spot step affect the score shown, or only `debugStats`? The
  default is only `debugStats`, so a wrong tap never costs a solve.
- A 10th Skillmap axis "Reading / Debug": not now, by the 11-22 decision.
  Revisit at 15 or more items and 28 days.

## Success Criteria (ledger claim, written before data)

The metric `debug_solve_through` is defined first, in `docs/agent/metrics.md`,
in its own PR (rule 6b). Confound to state: a prefilled editor inflates first
runs and solve-through against blank-editor items, so compare it against
itself over time and against same-band challenges only as a floor. The
baseline comes from the same 28-day window.

- **Metric:** challenge solve-through for the Debug set vs same-difficulty
  challenges, over 28 days from the flag flip. Also the share of people who
  open a Debug item and then reach 6 or more total solves.
- **Target:**
  - Debug solve-through within 10 points of same-band challenges, so it is not
    a dead end;
  - at least 40 people open a Debug item in 28 days.
- **Falsification:** fewer than 20 openers in 28 days with discovery live means
  nobody wants it. Freeze the set at 12 and write it down. Solve-through more
  than 20 points below the band means the format is broken. Fix the UX before
  adding items.
