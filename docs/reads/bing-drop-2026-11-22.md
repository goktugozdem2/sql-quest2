Asked by B1's funnel read (`docs/reads/funnel-2026-11-22.md`): Bing clicks
fell 280/wk → 25/wk and the `/sql-exercises/` door explains about half of
the six-solver drop. Question: why, and what in the repo can recover it.

Sources, read-only MCP, 2026-11-22: `bing_site_daily` (daily, through
11-19), `bing_crawl_daily` (daily levels, through 11-20), `bing_stats` page
and query slices (weekly buckets, a date = the 7 days ending on it; never
summed across slices), `bing_url_status` (419 sitemap URLs, checked

bingbot (`Mozilla/5.0 … compatible; bingbot/2.0 …`). Repo history from
`git log` on origin/main.

## 2. Two things fell, not one

- **A September bump went away.** "sql practice" (the head query) appeared
  in the week to 09-18 at 742 impressions, position 8, and held 862 / 907
  through 10-02; it fell to 230 (10-16) and 70 (11-06) as its position went
  8 → 10, i.e. off page one. At 1–2% CTR it was never many clicks, but it was
  ~1/5 of the site's impressions at the peak.
- **Then the base fell below August.** August ran 75–116 clicks/wk; November
  runs 25–37. Every practice query lost position together: "sql practice
  questions" 3 → 9 (weeks to 10-02 → 11-20), "sql exercises" 3 → 8, "sql
  practice exercises" 2 → 6. So did pages nobody touched: `/blog/sql-joins-explained/`
  401 → 39 impressions (10-02 → 11-13), `/blog/sql-cte-tutorial/` 246 → 9,
  `/sql-find-duplicates/` 122 → 1, `/challenges/window-functions/` 125 → 44,
  `/best-sql-practice-sites/` 209 → 64. None of those files changed between
  10-03 and 11-19. The brand query "sql quest" held position 3–4; its
  impressions (115 → 39) are demand, not rank.

A site-level loss of rank on Bing, starting in the last week of September
and stepping down on 10-17, with Google moving the other way on the same
page (`/sql-exercises/` on Google: position 15.7 → 7.9 → 15.2, clicks 10 →
18–19 → 11 a week, weeks from 09-19 → 10-03 → 11-14).

## 3. The hypotheses

**(a) The `/questions/` pages dilute or cannibalise — partly ruled out.**
Cannibalisation is ruled out: across every bucket since they shipped, the
question pages drew **1 impression** in Bing's page slice. Dilution cannot be
ruled out from this data. #72's bingbot noindex is shipped and served: a
question page answers 200 with `<meta name="robots" content="index, follow">`
and `<meta name="bingbot" content="noindex, follow">`; the hub `/questions/`
has no bingbot tag. 5 of the 307 question pages were crawled after 11-20,
so Bing has barely read it yet.

**But the index growth is not mainly the question pages.** `in_index` is
**830** on 11-20 against a sitemap of **422** URLs and **416** URLs Bing
counts as fetched with a 200 (`code_2xx`). Even if every sitemap page were
indexed, ≥ 408 indexed URLs are outside the sitemap. The one population of
that size Bing reports is the robots-blocked one:

**(f, new) The robots-blocked app URLs are in Bing's index as bare URLs —
supported, and it is the change that lines up with the peak.** On 09-23
robots.txt began to disallow `/app/?` and `/app?` (crawl budget, on Bing's
own "limited crawl capacity" advice). The static site links the app shell
under **1,173 distinct query strings** (307 from the question pages, 825 from
the rest — `?challenge=…&src=…`, `?company=…`). From that day:

- `blocked_by_robots` went 0 (09-24) → 11 (09-25) → 150 (10-02) → 349
  (10-16) → 602 (10-30) → **819** (11-20), never falling;
- `all_other_codes` went from a flat ~100 (the 308 twins: www, `.html`,
  no-slash) to **913** = ~100 + the blocked count;
- `in_index` went 163 → **830** in step with it, while `code_2xx` (pages
  Bing could fetch) stayed 416–465.

A blocked URL cannot have its `noindex` read, and a search engine may still
index it from links — `tests/technical-seo.test.js` already says so of
Google ("Indexed, though blocked by robots.txt"); the app shell is
`noindex, follow` but Bing is forbidden to see that. Bing clicks peaked the
week the rule shipped (280, from 09-19) and fell every week after. This is
an inference from Bing's aggregate counts, not a URL list: the API gives no
per-URL index state for non-sitemap URLs. The founder's check below settles
it in one screen.

**(b) Canonical / host — ruled out as the cause; one standing oddity.**
Every variant answers as it should, bingbot UA and default alike:
`/sql-exercises` → 308 `/sql-exercises/`; `/sql-exercises.html` → 308
`/sql-exercises/`; `https://www.sqlquest.app/sql-exercises/` → 308 bare;
`http://` → 308 `https://`; `/index.html` → 308 `/`; `/app.html` → 308
`/app/`. `/sql-exercises/` serves 200, `robots: index, follow`, canonical
`https://sqlquest.app/sql-exercises/`, identical bytes for bingbot and a
browser. No `www.` anywhere in the repo except the host redirect in
`vercel.json`. **But Bing has reported the homepage only as
`https://www.sqlquest.app/`** (29 weekly buckets from 05-01; the bare `/`
never), plus `/amazon-sql-interview/` and `/google-sql-interview/` under
`www.` — since May, so not the October cause. It is Bing's choice, not the
site's; the fix is in Bing's UI (FOUNDER).

**(c) A content or title change to `/sql-exercises/` — ruled out as the
main cause.** The page changed on 09-11 (title + links — the start of the
rise), on 09-30 (title 86 → 67 characters, the five worked solutions) and
next on 11-20 (#65). The 09-30 version is the one Bing recrawled before the
10-17 step (Bing title pickup runs 1–3 weeks), so it cannot be excluded for
"sql practice" alone; but the same version **rose** on Google (15.7 → 7.9),
and the untouched blog and tool pages fell on Bing in the same weeks. The
67-character title pin (`tests/snippet-length.test.js`) is not involved.

**(d) Crawl or status problems — ruled out.** Crawl errors 0–14 a week,
4xx 0–1, 5xx 0. `/sql-exercises/` last crawled 11-13 (70,441 bytes = the
current page). 131 of the 419 sitemap URLs crawled in the 28 days to 11-20;
41 question pages never crawled. Nothing in the status data broke.

**(e) A Bing-wide change — not shown, not excluded.** No confirmed Bing
algorithm update for October 2026 in public reporting (one search, an
SEO-vendor roundup of 10-21 says none was confirmed). Bing also tested
snippet presentation that month, and Copilot answers absorb clicks on
definitional queries — that would cut CTR, but this fall is position and
impressions. Google flat (125–211/wk) rules out a demand collapse.

## 4. What the read supports, and what ships

1. **Let bingbot fetch the app URLs, so it reads their `noindex`** (code PR,
   this run): robots.txt gets a `User-agent: bingbot` group with the default
   list minus `/app/?`, `/app?`, `/app.html`; every other group keeps the
   09-23 rule. Cost: Bing spends crawls on ~1,173 copies of one small shell
   until it has seen each say noindex; guardrail below.
2. **Read #72 and this together.** Both remove thin URLs from Bing's index in
   the same weeks; neither can be credited alone. Worse, #72's mechanism check
   (`in_index` down ≥ 250) would now be met by the app URLs leaving, not by
   the question pages — #72's verdict must read the question pages' own Bing
   state, not `in_index`.
3. Not done: `rel="nofollow"` on the 1,173 links (a second mechanism in the
   same window), any further `/sql-exercises/` title change (#65 is 2 days
   old and has its own read on 12-12), and any noindex/prune (the prune
   freeze to 11-09 has passed, but nothing here points at a page that should
   leave).

## 5. FOUNDER (Bing Webmaster Tools, site picker on `sqlquest.app`)

1. **Settle (f) in one screen:** Site Explorer
   (`/webmasters/siteexplorer?siteUrl=https://sqlquest.app/`) → open the
   `app` folder → filter **Blocked by robots.txt** and **Indexed**. Write
   down the counts. If the `app` folder holds hundreds of indexed URLs, (f)
   is confirmed; if it holds ~0, it is wrong and the PR should be closed.
2. **After the PR deploys:** URL Inspection on
   `https://sqlquest.app/app/?challenge=91&src=sql-exercises` → expect
   "Excluded by NOINDEX" rather than "Blocked by robots.txt" within days.
3. **www:** URL Inspection on `https://www.sqlquest.app/` — it should say
   the URL redirects to `https://sqlquest.app/`. Then Configure My Site →
   check there is no separate `www.sqlquest.app` site carrying settings, and
   **Submit URLs** for `https://sqlquest.app/` and
   `https://sqlquest.app/sql-exercises/` (two of the 100/day).
4. Look at **Recommendations** once: if "limited crawl capacity" returns
   after the deploy, note the date; the claim's guardrail decides.
