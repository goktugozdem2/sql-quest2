## New in the window

1. **The free-quota wall smoke check writes a fixed guest row to production
   when it runs without hermetic mode.** `scripts/smoke-test.js` (PR #92)
   seeds `guest_1795300000000` with 10 solves and no XP. Local runs without
   `SMOKE_HERMETIC=1` send real saves, so the second run onwards hit
   `sq_save_user`'s guard: 12 times "regression refused: solved 10 -> 10, xp
   415 -> 115", 21:49 → 00:09 UTC on 11-21, during that PR's development.
   The refusal-recovery merge then saved the row (updated 00:09:40). There
   were no `save_refused` events because localhost mutes analytics. It was
   not a person. The 21 `create-checkout-session` OPTIONS 403s in the same
   window came from the same machine (TR, macOS) on dev ports outside
   `ALLOWED_ORIGINS`. Nothing has come since 00:09. The fleet protocol
   already requires `SMOKE_HERMETIC=1`. Leave `guest_1795300000000` out of
   any read of the `users` table (it is synthetic).
2. **Every mail cron's `net._http_response` row is a timeout, so the status
   cannot be read there.** None of the seven `cron.job` commands sets
   `timeout_milliseconds`, so pg_net waits its default 5 s. The functions take
   longer. Execution times from `function_edge_logs`: streak-reminder
   5.5–16.6 s (all 24 hourly runs), skill-decay 18.9 s, welcome-back 17.3 s,
   checkout-abandon 11.7 s, capture-email-drip 6.5 s, trial-reminder-cron
   6.4 s. All six rows kept in `net._http_response` (it holds about 6 h) have
   status NULL and read "Timeout of 5000 ms reached". The functions finished
   anyway: every run returned 200 in `function_edge_logs`, and
   `email_events` shows sends every day. The harm is that a real 401 or 500
   from a mail cron would look like these timeouts. Until the timeout is
   raised, read cron health from `function_edge_logs` (status by function),
   not from `net._http_response`.
